# 制作与验收详细步骤

目录、登录和启动入口以 ../SKILL.md 为准。以下命令名是 workflow.py 的子命令；指定目录模式统一通过 `run.py task TASK_DIR COMMAND ...` 调用，自动带入路径。

场景和动作必须适配实际商品。牛仔裤使用日常穿搭、走近、转身、腰线/口袋/裤腿展示；下文肩带、水边和水花只是泳装示例，不能写进牛仔裤提示词。

## Stage 与下一步

严格按以下映射选择唯一下一步：

```text
selected -> register-reference -> reference-ready
reference-ready -> validate-product-copy -> mark-image-prompt 1 -> awaiting-image-1 -> ingest-image 1 -> image-1-ready
image-1-ready -> mark-image-prompt 2 -> awaiting-image-2 -> ingest-image 2 -> image-2-ready
image-2-ready -> mark-image-prompt 3 -> awaiting-image-3 -> ingest-image 3 -> frames-ready
image-1-ready -> retry-image 1 -> reference-ready
image-2-ready -> retry-image 2 -> image-1-ready
frames-ready -> retry-image 3 -> image-2-ready
frames-ready -> mark-video-prompts -> awaiting-videos -> claim-video-attempt 1|2 -> 按积分升序尝试低于 300 积分/次的视频模型并验收 -> ingest-videos -> videos-ready -> merge -> merged
merged + 用户明确重做同一产品视频 -> redo-videos -> frames-ready
任何未完成阶段 + 用户确认手工成片 -> register-manual-video SOURCE -> merged
```

- `selected`：自动选择并登记无身份参考图，不在此阶段停留或交付。
- `reference-ready`：自动生成并校验店铺产品资料，再只编写第 1 张图片提示词并运行 `mark-image-prompt 1`，不在此阶段停留或交付。
- `awaiting-image-1`：等待并接收第 1 张下载图。
- `image-1-ready`：检查实际第 1 帧后，只编写第 2 张图片提示词。
- `awaiting-image-2`：等待并接收第 2 张下载图。
- `image-2-ready`：检查实际第 2 帧后，只编写第 3 张图片提示词。
- `awaiting-image-3`：等待并接收第 3 张下载图。
- `frames-ready`：复核三帧并编写两个视频提示词。
- `awaiting-videos`：自动使用已登录的视频生成网页，按积分从低到高尝试低于 300 积分/次的可用模型，生成、下载并验收两个视频；所有合资格模型都失败或自动机会耗尽后才等待用户。
- `videos-ready`：合并视频。
- `merged`：检查实际成片，生成 TikTok 发布内容与视频链接标题；需要新任务时再选品。

### 重做同一产品视频

用户明确要求重做最近完成的同一产品视频时，对该任务运行 `redo-videos`。该命令允许从 `merged` 或旧入口遗留的 `awaiting-videos` 阶段执行，把当前视频目录顶层的提示词、视频和发布文本复制到 `视频制作/重做归档/NNN`，保留原文件、三张规范帧和商品资料，清空旧合并记录与视频尝试次数，并回到 `frames-ready`。不要手工修改状态，也不要用 `select` 或 `replace` 重新选择同一商品。

命令成功后，依据当前 `references/prompt-rules.md` 重写两个视频提示词，再运行 `mark-video-prompts` 并完整执行自动视频、验收、顺滑合并和发布文案流程。新暂存片段和新成片必须使用未占用文件名，不得覆盖旧视频；固定名称的提示词和发布文本可以在归档成功后更新，旧版本以归档副本为准。

## 登记无身份参考图

1. 在 `selected` 后读取用户指定目录归档中的真实产品图片，优先使用 `扫同款产品图.jpg`，并用 `view_image` 检查；没有该文件名时使用实际产品图，不要求重命名源文件。
2. 检查该实际图片能否清楚呈现服装类型、剪裁、图案、覆盖度和材质；资料损坏、模糊或明显不合款时停止并报告，不得换用另一款图片继续。
3. 检查脸或可识别头部。若可见身份，计算 `--crop X Y W H`，移除完整头部身份，同时尽量保留服装；不要只遮脸而留下可识别头部。没有身份可不裁剪。
4. 运行 `register-reference SOURCE [--crop X Y W H]`，SOURCE 使用刚检查过的当前产品图片绝对路径；可以是源产品目录或当前归档内的实际文件，文件名不限。
5. 登记后立即用 `view_image` 检查 `图片制作/00-product-reference.png`。若仍能看到身份，保持在允许登记的阶段，重新计算裁剪并再次运行 `register-reference`，然后重新裁剪并复查。
6. 开始任何提示词前，完整读取 `references/prompt-rules.md`，只使用参考图中可见的服装事实。

## 店铺产品资料

1. 产品到达 `reference-ready` 后，先读取实际 `00-product-reference.png`、当前任务归档中的商品文案和尺寸资料（例如 `TK店铺标题和内容.txt` 和 `尺寸配置图.png`，也接受其他文件名）；必须先整理店铺产品资料，再编写第 1 帧提示词，不要从图片重新编造链接目录已经提供的商品事实。
2. 把 `店铺产品标题.txt`、`店铺产品内容.txt`、`店铺产品尺寸.txt` 写入 `status` 返回的绝对 `task_dir`。三个文件必须是 UTF-8 普通文件，不要放入 `图片制作` 或 `视频制作`。
3. `店铺产品标题.txt` 优先使用原资料中已确认的英文标题（例如 `Title:` 字段）；没有成稿时根据真实产品资料整理。保持单行、不超过 150 字符、不含标签，不编造品牌、功能、认证或优惠。
4. `店铺产品内容.txt` 使用实际资料中已确认的英文商品参数清单，每行 `Field: Value`。原稿有 `Content:` 字段时优先保留其事实；没有时从真实资料或图片中的可见事实整理，不猜测面料成分、弹性、洗护、产地、货号或性能，不承诺未经证实的塑形、防晒、速干等功能。
5. `店铺产品尺寸.txt` 转录实际提供的尺码文字或尺寸图（文件名不限），图片须用 `view_image` 查看；保留尺寸与单位，不根据模特或常见尺码猜测。没有资料时写 `未提供尺码信息`，并交付时指出缺失。
6. 三个文件完成后运行 `validate-product-copy`。只有校验成功后，才使用返回 JSON 中的 `product_title`、`product_content` 和 `product_size` 交付店铺资料并继续第 1 帧提示词；校验失败时不得继续生图。
7. `status` 恢复到 `reference-ready` 时，必须先检查这三个文件是否存在并重新运行 `validate-product-copy`；文件缺失或产品已换品时重新依据当前参考图生成，不得复用上一款产品资料。

## 自动生图与重试上限

先读取任务的 `image_mode`。新电脑默认 `website`：直接进行网页阶段，不调用 API、不虚增 API 次数；网页每帧最多 3 次。只有 `api-first` 任务才按下面的 API 两次再网页三次执行。网页操作使用 Codex 内置浏览器；需要登录时遵守 SKILL.md 的按需登录流程。


用户授权制作视频后，按任务的 image_mode 自动生图。每次提交前必须先运行 `claim-image-attempt N api` 或 `claim-image-attempt N website` 原子占用次数，不能只在内存中计数，也不能在请求完成后补记。

1. 对每一帧，接口阶段最多 2 次，即首次接口生成 + 1 次接口重试。每次先运行 `claim-image-attempt N api`，再用生图 API script 提交。请求失败、任务失败或结果未通过视觉门禁都消耗本次机会。
2. 当前帧的两次接口机会都用尽后切换网页。对每一帧，网页阶段最多 3 次，即首次网页生成 + 2 次网页重试。每次先运行 `claim-image-attempt N website`，再使用 Codex 内置浏览器打开 `https://toapi.top/ai-image` 生成；若未登录，先把页面显示给用户登录，登录不消耗尝试次数，确认登录成功后才 claim 并提交。
3. 当前帧达到对应模式上限（website 为 3 次网页，api-first 为 2 次接口 + 3 次网页）后，保留当前任务、提示词和已有文件，报告失败原因，交付手工生成入口。CLI 返回 `next_on_failure: manual` 后不得继续自动提交。

`claim-image-attempt` 只持久化次数，不改变 stage。命令在真正提交前执行，因此进程中断或结果未知也按已消耗处理，防止跨对话或并发运行突破上限。恢复到 `awaiting-image-N` 时先从 `status` 的 `active_task.image_attempts` 读取当前帧已有的 API 与网页次数；不要重复运行 `mark-image-prompt N`，也不要假设仍从第 1 次开始。

首次 claim 接口次数前，先用生图 API script 运行 `check --model gpt-image-2`；该命令只调用模型列表接口，验证 `OPENAI_API_KEY`、`OPENAI_BASE_URL`、中转站连接和模型可用性，不提交生图，因此不消耗生图尝试次数。Key 只能由脚本从环境变量读取，不得把 Key 写进命令、文件、日志或对话，也不得输出完整 Key。脚本必须关闭 SDK 自动重试，确保一次 `claim-image-attempt` 只对应一次可能计费的 API 提交。

部分中转站可能跟随输入图比例。生图 API script 会在隔离临时目录中把唯一参考图等比缩放并留白适配到目标 9:16，再调用 `/images/edits`；保留原始参考图。返回图比例不接近 9:16 时失败且不留下候选；比例合格时再规范为 `720x1280` PNG。

接口尝试使用以下固定调用；把 `N` 对应的提示词文件、当前 `image_dir` 和参考图绝对路径代入，不要把方括号输入 shell：

```text
"$PYTHON" "<SKILL_DIR>/scripts/openai_image.py" generate --prompt-file PROMPT --reference REFERENCE --model gpt-image-2 --size 720x1280 --quality low --count 1 --output-dir IMAGE_DIR
```

网页尝试固定选择 `GPT Image 2`、`图生图`、`9:16`、生成数量 `1`，上传同一张唯一参考图并填写当前提示词。生成成功后把恰好一个新结果下载到 `image_dir`；浏览器不能直接定向下载时，点击“复制图片链接”，再运行 `<SKILL_DIR>/scripts/toapi_image.py download-url URL --output IMAGE_DIR/网页生成-N-ATTEMPT.png`，其中 `ATTEMPT` 使用本次 `claim-image-attempt` JSON 返回的网页尝试序号。下载失败时可以对同一个已生成 URL 重试下载，不得为下载重试再次 claim 或重新生成。`toapi_image.py` 只服务网页降级下载，不得用于接口阶段生图。不要选择 Pro 模型，不要一次生成多张。

任何尝试产生候选图后，确认相对当前 baseline 恰好只有这一个新候选，再运行 `ingest-image N` 并用 `view_image` 检查规范帧。若规范帧不合格，运行 `retry-image N` 退回，再保持原提示词或按具体缺陷重写；第 1 帧退回 `reference-ready` 后先重新运行 `validate-product-copy`，然后运行 `mark-image-prompt N` 回到 awaiting 阶段。`image_attempts` 不会被重置，再按 CLI 返回的 `next_on_failure` 继续接口、网页或人工分支。请求在生成候选前明确返回失败时不要运行 ingest 或 retry，可按下一次 claim 继续。若请求超时、断连、进程中断或结果未知，中转站没有可恢复的任务 ID；保留已消耗次数并停止，报告该次状态，不得自动再次提交，以免重复计费。

每次自动调用都必须上传当前 `00-product-reference.png` 作为产品参考。不得为了绕过错误或内容策略而改成另一款服装、降低产品一致性、删除用户要求的产品参考或接受不合格结果。

自动调用每次只附加这一张输入图，并在提示词正文中统一称为“图1”；不要在同一次请求附加历史帧或其他图片，也不要把本地文件名或路径写入交付提示词。

## 手工生图的单图约定

用户手工生图时，每次只要求上传 1 张图片，提示词正文一律称它为“图1”。正文不得出现本地图片文件名、绝对路径或“同时上传多张图”的要求。按帧使用唯一输入：第 1 帧把无身份产品参考图作为图1；第 2 帧把已验收的实际第 1 帧作为图1；第 3 帧把已验收的实际第 2 帧作为图1。

编写提示词时仍要在内部读取 `00-product-reference.png` 和所有已验收规范帧，提取服装硬锚点、人物与场景连续性；这些文件只供分析和验收，不要求用户一起上传。第 2、3 帧必须把原产品结构硬锚点完整写进正文，依靠图1与文字双重锁定，不能因单图输入而降低产品一致性。

## 严格串行制作三帧

每次只写当前提示词；不要预写后续提示词。后续帧必须依据刚接收并检查过的实际上一帧，而不是依据先前设想。

严格遵循三条交接链：

```text
写 01-start-prompt.txt -> mark-image-prompt 1 -> 等待用户下载 -> ingest-image 1 -> view_image 01-start.png
写 02-bridge-prompt.txt -> mark-image-prompt 2 -> 等待用户下载 -> ingest-image 2 -> view_image 02-bridge.png -> 写 视频制作/01-video-prompt.txt
写 03-end-prompt.txt -> mark-image-prompt 3 -> 等待用户下载 -> ingest-image 3 -> view_image 03-end.png
```

第 2 帧接收并用 `view_image` 验收通过、到达 `image-2-ready` 后，立即根据实际 `01-start.png` 与 `02-bridge.png` 编写第一段 `视频制作/01-video-prompt.txt`，完成后才开始编写 `03-end-prompt.txt`。不要等到写第 3 帧时才生成第一段视频提示词。只提前写第一段视频提示词，不得预写 `02-video-prompt.txt`，也不得提前运行 `mark-video-prompts`。第一段视频提示词必须完整描述 `01-start.png -> 02-bridge.png`，不依赖尚未生成的第三帧。

对每一帧执行以下步骤：

1. 只在当前 stage 允许时，把当前提示词写入 `image_dir` 下对应的 `01-start-prompt.txt`、`02-bridge-prompt.txt` 或 `03-end-prompt.txt`；第 2 帧验收通过后先按上面的规则写第一段视频提示词，再写第 3 帧提示词。
2. 写好提示词后才运行对应的 `mark-image-prompt 1|2|3`，让 CLI 记录下载 baseline。不要在写提示词前运行 mark。
3. 若当前任务启用自动生图，按“自动生图与重试上限”直接执行接口到网页的降级链；只有自动机会用尽后才交付“当前 prompt 全文 + 准确下载目录”并停止等待用户。未启用自动生图时，直接交付 prompt 与目录并停止。准确下载目录必须取自 status 的绝对 `image_dir`；当前帧验收前不要继续写下一帧。
4. 用户手动生成并把一张新图片下载到该目录后，运行对应的 `ingest-image 1|2|3`。
   只有默认接收因候选已存在于 baseline 而报告 0 个新候选，或用户明确接受 `退回归档` 中的具体图片，且用户明确确认该文件就是当前帧并给出准确路径时，才运行 `ingest-image N --confirmed-source SOURCE`。SOURCE 必须是当前绝对 `image_dir` 或其 `退回归档` 中的真实 JPEG、PNG 或 WEBP 文件，不能是参考图或规范帧。仍由脚本执行解码、9:16、无覆盖、规范命名、原子状态和回滚校验；不得手工复制、改时间戳或修改状态。
5. 接收后立即用 `view_image` 检查规范文件：`01-start.png`、`02-bridge.png` 或 `03-end.png`。
6. 检查画面接近固定 9:16。允许导出造成少量像素舍入误差，按宽高比容差判断，不要求尺寸恰好整除；明显偏离 9:16 时判为不合格。
7. 检查人物为 25-35 岁成年新身份，没有复制参考脸；检查服装事实与参考图一致；检查三帧的人物、场景、光线、镜头连续；检查相邻帧有明显动作推进，而不只是表情或发丝变化；检查画面符合 `references/prompt-rules.md` 的默认手机 UGC 质量基准，包括自然微胖体型、未修饰皮肤、真实腹部状态和手机近景透视；检查没有肢体/手部畸形、重复人物、文字、水印或品牌标志。
   若用户明确只要求服装一致，并明确接受脸部身份或体型在帧间变化，则当前任务改用服装结构一致性作为跨帧人物相关硬门禁，不得仅因脸部身份或体型变化退回。后续图片和视频提示词以实际上一帧为唯一输入，不再要求复现前一帧脸部或体型，但仍完整重述原产品结构硬锚点，并仍检查成年人物、9:16、肢体与手部正常、动作可达、无文字水印及无生成缺陷。
8. 不合格时不要推进到下一条 mark 命令。在仍处于 `awaiting-image-N` 且尚未 ingest 时，移走不合格下载候选，保持恰好一个新候选后重新生成。若已经 ingest 并进入对应 ready stage，运行 `retry-image N`：第 1 张只允许从 `image-1-ready` 退回 `reference-ready`，第 2 张只允许从 `image-2-ready` 退回 `image-1-ready`，第 3 张只允许从 `frames-ready` 退回 `image-2-ready`。命令会把存在的当前规范帧移入 `图片制作/退回归档` 且拒绝覆盖；规范帧已由用户移走时只修复状态。保留参考图、提示词、前序规范帧和其他文件，不要手工修改 `工作流进度.json`，不要私自覆盖规范帧。退回后重写当前提示词并重新运行同一索引的 `mark-image-prompt N`。

编写 `02-bridge-prompt.txt` 时读取实际 `01-start.png`；编写 `03-end-prompt.txt` 时同时读取实际 `01-start.png` 与 `02-bridge.png`，让动作自然推进并维持连续性。这里的多图读取只发生在 Codex 内部；交付给用户的手工生图提示词仍必须遵守“单图约定”，只把实际上一帧称为图1。

## 编写与接收视频

1. 到达 `frames-ready` 后，再用 `view_image` 并排复核 `01-start.png`、`02-bridge.png`、`03-end.png`，确认全部视觉门禁仍成立。
2. 先复核已经提前写入绝对 `video_dir`（即任务的 `视频制作`）的 `01-video-prompt.txt`，确认它仍准确描述实际 `01-start.png -> 02-bridge.png`；若缺失或内容与规范帧不符，立即重写。然后只根据实际 `02-bridge.png` 与 `03-end.png`（即 `02-bridge.png -> 03-end.png`）编写 `02-video-prompt.txt`。最终保留两个独立普通文件，不要覆盖或省略第一段。
3. 把每个视频 prompt 写成可独立执行的 15 秒片段，并完整落实 `references/prompt-rules.md` 的手机 UGC 质量基准。两个片段的有效口播都必须至少覆盖各自片段的三分之二；15 秒片段累计有效口播不得少于 10 秒。人物必须在前 0.5 秒开始说话，把口播自然延续到至少 12.8 秒附近，并在 14.2-14.6 秒前自然说完，避免开头说完一个过短句后长时间沉默。可以使用一条完整长句或两条衔接自然的短句；所有口播都必须由画面内人物说出、清楚可辨、内容不冲突且不能被片段边界截断，并明确人物嘴型、呼吸、表情和动作同步。第一段前 0.5 秒必须边开口边形成近距离视觉钩子，第二段前 1 秒必须用新的转身、调整肩带/侧带、走近、版型展示或安全的水花微事件形成不同视觉爆点。优先考虑“人物朝镜头移动、拍摄者后退跟随、到达水边后产生真实即时反应”的移动叙事，但必须保持同一场景的可达路径和连续运动。用户提供高曝光参考时只迁移口播节奏、动作节奏、空间推进和手持真实感，不迁移参考商品、品牌或功效。每个文件都独立写全主体、服装、场景、动作、镜头、首尾锚点、英语口播、嘴型同步、口播时间范围、环境声和逐时段动作；正文必须明确写出“有效口播至少覆盖三分之二片段”，否则不得运行 `mark-video-prompts`；不能只写“同上一段”。
4. 两个文件都完成后运行 `mark-video-prompts`，让 CLI 记录视频 baseline。当前工作流启用自动视频，不要在 `awaiting-videos` 停下交付提示词。
5. 每段提交前必须运行 `claim-video-attempt 1|2`；每段最多 3 次自动机会。每次机会只对应一个明确的“模型 + 单次积分 + 网页提交”，首次生成和因请求失败、审核失败、媒体失败、口播失败或视觉门禁失败而重做都消耗次数。优先每个合资格模型各尝试 1 次；同一模型只有在仍有自动机会且没有更便宜的未尝试模型时才允许再次尝试。维护当前任务的模型尝试记录（模型名、网页地址、页面显示积分、提交结果和失败原因），不得因换模型重置或绕过 `claim-video-attempt`。CLI 返回 `next_on_failure: manual` 后不得再自动提交；保留已通过片段与退回归档，交付当前视频提示词和目录，然后停止并等待用户手工生成该段。
6. 自动视频使用已登录的视频生成网页，不固定绑定单一模型，也不探测、抓取或调用隐藏 API。开始每段前先查看可用模型页面，读取页面实际显示的模型名、单次积分和输出规格，只保留单次积分严格低于 `300` 的模型，并按积分升序排列；不符合 `720p`、15 秒、竖屏 `9:16` 或不能接收 2 张参考图的模型跳过。优先选择最低积分模型；该模型失败后，立即选择列表中下一个更便宜到更贵的未尝试模型。只有全部合资格模型都试过仍有剩余机会时，才重试积分最低且网页状态明确可提交的模型。每次切换模型必须重新确认网页上的模型名、积分、`720p`、15 秒和 `9:16`，并在本地尝试记录中写明选择依据。

   第一段上传 `01-start.png` 与 `02-bridge.png`，填写 `01-video-prompt.txt`；第二段上传 `02-bridge.png` 与 `03-end.png`，填写 `02-video-prompt.txt`。每次只上传对应的两张规范帧，不传产品参考图或其他图片。确认生成历史已出现本次任务后，下载成片到 `video_dir/自动生成暂存`，不要直接混入下载候选。
7. 未登录时将当前模型页面显示给用户完成登录；积分不足、页面实际积分达到或超过 `300`、网页显示生成失败、提交中断或下载失败时，保留任务、提示词、模型尝试记录、暂存文件和已消耗的尝试次数。若一次提交状态未知，不得用同一模型再次提交；只有确认失败或生成历史明确失败后，才能依照积分升序切换到下一个合资格模型。达到每段 3 次上限，或没有其他合资格模型时切换为手工生成；不得回退到 Otuapp、其他隐藏 API 或不符合价格上限的模型。

网页模式未登录时，返回 SKILL.md 的“按需登录”流程：打开内置浏览器当前模型页，用户登录后再 claim。不要因为登录重新从第 1 次计数，也不要重复创建 API token。若 Codex 浏览器没有上传/下载控制工具则停止在当前任务并准确说明，不伪造成功。
8. 每段下载后先运行媒体探测，确认有音轨、约 15 秒、竖屏 9:16、至少 720x1280、至少 24fps。优先使用本机离线转写的逐句时间戳核对实际口播起止时间并累计有效口播时长；转写不可用时必须实际完整试听，并结合波形或音频活动区间核对，不得只检查音轨存在。每段清楚、由画面内人物嘴型同步说出的有效英语口播必须至少占实际片段时长的三分之二；约 15 秒片段不得少于 10 秒，句间长静音、音乐和环境声不计入口播时长。全部口播都要清楚、句尾未截断，且不包含与当前产品或场景冲突的品牌、价格、颜色和功效；未达到比例时按口播失败退回重做。
10. 在隔离临时目录中均匀抽取至少 4 张关键帧；对疑似手部、服装或液体缺陷的区间加密抽帧。用 `view_image` 检查视觉爆点、同一人物与服装、真实重心和软组织运动、手机手持感，并排除肢体融合、手指畸形、服装漂移、异常水柱、腿间液体、文字、水印和模型标志。不合格时把暂存结果保留并记录具体缺陷，通过或退回后删除临时关键帧。
11. 发现缺陷时先判断能否局部剪除。只有缺陷集中在连续的短区间，且剪除后仍保留完整、清楚、由画面内人物嘴型同步说出的英语口播，有效口播累计时长仍至少占剪后片段的三分之二，并仍有可见视觉爆点、完整服装展示和自然动作时，才允许剪辑挽救。不可通过剪辑保留乱码口播、截断句子、嘴型漂移、身份或服装结构变化、肢体畸形、违规画面；缺陷覆盖大部分片段、剪后只剩零碎画面、口播比例不足或需要用画外音掩盖时必须退回重做。
12. 剪辑挽救前保留原片到 `video_dir/退回归档`，亲自用转写时间戳与加密关键帧确定精确保留区间。需要把挽救片段与另一段合成完整成片时，运行 `salvage_merge.py`：用 `--first-start/--first-end` 与 `--second-start/--second-end` 传入经过验收的保留区间，`--transition` 使用 `0.25-0.45` 秒。人物位置、景别或姿态有明显变化时，`--transition-style` 优先使用 `hblur`；若逐帧仍有重影，则根据画面运动方向改用 `wipeleft`、`wiperight`、`slideleft` 或 `slideright`。`smoothleft`、`smoothright`、`smoothup`、`smoothdown` 和 `fade` 只允许在两段构图高度一致、逐帧确认不会出现双重人物时使用。脚本同时让前段环境声渐退、后段开头口播保持清楚；不得在句子中间设置转场。输出必须直接放在当前 `video_dir`，不得覆盖已有文件。
13. 对剪辑成片重新执行媒体探测、离线转写和至少 6 张关键帧检查，并在合并点前后加密抽帧，确认口播未被压低或截断、整片有效口播累计时长至少占实际成片时长的三分之二、画面没有明显重影、黑帧、冻结或硬切。通过后运行 `register-manual-video SOURCE` 进入 `merged`；不通过时保留剪辑候选，不得登记。
14. 无需剪辑挽救且两段都通过后，按顺序把第一段、第二段发布为 `video_dir` 顶层恰好两个新候选，确保第二段修改时间更晚且可区分，然后运行 `ingest-videos`。CLI 将最旧候选规范为 `01-segment.*`、最新候选规范为 `02-segment.*`。随后立即运行 `merge`，不要停在 `videos-ready`。

## 合并与交付

1. 在 `videos-ready` 运行 `merge`。媒体兼容时优先无损 copy；不兼容时先规范化为 H.264/AAC，再合并。
   若两段的景别、姿态或镜头距离存在明显跳变，且用户允许剪辑修复，不使用这里的硬拼接；按上一节的局部修复流程运行 `salvage_merge.py`，使用短交叉淡化合成并经完整门禁后登记为手工成片。
2. 确认输出为 `视频制作/final.mp4`，并确认保留两段 segment：`01-segment.*` 与 `02-segment.*`。
3. 对 `final.mp4` 运行媒体探测、离线转写并实际试听，确认两段口播都保留、清楚可辨且合并点没有切断词句，并确认整片有效口播累计时长至少占实际成片时长的三分之二。再从开头、前段、中段、后段和结尾均匀抽取至少 5 张关键帧，用 `view_image` 复核合并点、竖屏画幅、人物与服装连续、手机 UGC 真实感以及两个不同的视觉爆点；检查后删除临时关键帧。发现口播比例不足、静音、只有音乐或环境声、口播被截断、嘴型漂移、冻结、黑帧、跳切、身份漂移、服装变形、肢体畸形或水印时不得交付为合格成片。
4. 向用户交付 `final.mp4` 的绝对路径，不要只给相对路径。自动工作流在成片门禁通过后继续生成并校验 TikTok 发布内容，不在这里提前结束。
5. `merged` 阶段重复运行 `merge` 是幂等操作；CLI 会验证现有成片，不应重复转码或删除 segments。

强制收尾：无论是 `merge` 还是 `register-manual-video` 进入 `merged`，都必须紧接着完成“手工成片与 TikTok 发布内容”中的成片检查、文案写入和 `validate-publish-copy`。在绝对 `video_dir` 中同时存在已校验的 `tk发布内容.txt` 与 `视频链接标题.txt` 之前，不得把视频合并任务视为完成，也不得只在对话中返回文案而不落盘。

## 手工成片与 TikTok 发布内容

同时支持按步骤制作和手工成片两种入口。用户说视频已经生成后，先运行 `status`，再按实际状态选择唯一入口，不要要求用户补做已经跳过的图片或分段视频步骤。

1. 按步骤制作时，若 stage 为 `videos-ready`，先运行 `merge`；若已经 `merged`，优先使用 `final.mp4`。读取状态中的 `merge.output` 作为实际成片绝对路径。
2. 手工成片时，要求用户把完整视频放入当前绝对 `video_dir`。若有多个视频且用户没有指明文件，先列出文件并请用户确认，不要猜测。用户确认具体文件后，在登记前先运行媒体探测，确认包含音轨；使用离线转写时间戳并实际试听，确认清楚真人口播由画面内人物嘴型同步说出，且有效口播累计时长至少占实际视频时长的三分之二，不能只有音乐或环境声。再均匀抽取至少 5 张关键帧，用 `view_image` 按默认手机 UGC 质量基准检查竖屏画幅、清晰度、人物与服装稳定、真实身体运动、手机手持感、视觉爆点和生成缺陷；不合格时不要登记，口播比例不足或没有爆点同样不得登记。通过后运行 `register-manual-video SOURCE`；该命令允许从任何未完成阶段登记成片、进入 `merged`，并保留手工视频原文件。
3. 不要只根据文件名或先前提示词写发布内容。先用媒体探测读取实际视频时长，再在隔离临时目录中从开头、前段、中段、后段和结尾均匀抽取至少 5 张关键帧。对每张关键帧使用 `view_image`，检查视频中实际出现的服装、人物动作、场景、镜头变化和度假氛围；检查完成后删除临时关键帧。
4. 根据实际视频内容和当前产品中可见的事实，生成自然、简短、适合 TikTok 直接复制的发布正文。不要编造视频里没有出现的动作、场景、功效、折扣、材质性能或品牌承诺。
5. 把可直接复制的视频内容写入绝对 `video_dir` 下的 `tk发布内容.txt`。标签放在正文后面，最后一行只写标签；正文和标签必须放在同一个文件中，标签使用空格分隔、最多 5 个，不要在标签后继续写正文。
6. 把挂商品链接时显示的标题单独写入 `视频链接标题.txt`。标题必须只有一行、不超过 30 个字符、不含标签；突出实际视频中可见的服装类型、颜色、剪裁或度假场景，不要写未经证实的品牌和功效。不要把它与选品后生成的店铺产品标题混用。
7. 写完两个文件后运行 `validate-publish-copy`。只有校验成功后，才使用返回 JSON 中的 `link_title` 与 `content` 向用户分别交付视频链接标题和完整视频内容；不要在校验后重新读取文件路径。视频内容必须保持正文在前、标签在后，用户可以直接复制。
8. 用户随后要求下一个产品时，为用户指定的下一款运行新的 `run.py start PRODUCT_DIR`；历史目录模式才运行 `select`，不读写已 `merged` 任务的 state。只有用户明确表达“替换当前未完成任务”并确认完成或放弃时，才对当前 `task_dir` 运行 `replace --force`；新旧任务仍各自保留独立进度、归档和手工视频。

## 提示词正文禁令

把脚本的 `FORBIDDEN` 模型名检查视为硬门禁。规则文档可以说明 `Veo 3.1` 与 `GPT Image 2 Pro` 禁令，但任何交付提示词正文不得包含这些字符串，也不得作为标题或前缀。保存 prompt 后先自行搜索，再运行 mark 命令。

## 安全验证

验证本 Skill 时禁止对真实根目录运行会改变任务的命令，尤其禁止真实 `select`、`replace`、登记、接收或合并。也不要为验证而对默认真实根目录运行 `status`，因为 status 会检查并可能恢复真实状态。

只做以下验证之一：只读检查 `SKILL.md`、规则与元数据；运行不接触真实任务目录的文档契约测试；或为 CLI 测试显式把 `--catalog`、`--done-root`、`--task-dir` 或 `--state-file` 等全局参数放在子命令前并指向隔离的临时根目录。测试结束后删除临时数据，不要触碰 catalog、done 和 state 的真实内容。
